# agent-unity-wrapper

Pure skill plugin — no binary of its own. It wraps the **external Unity MCP server**: a skill teaches Claude how to drive it, and (once wired) the manifests point at that MCP. This repo ships **only** three skills + manifests; the Unity MCP itself is a separate, pre-existing server.

> **Wired.** The Unity MCP (`mcpforunityserver==9.7.1`) is now wired into both manifests under the server key `unityMCP`. The scaffold state is resolved: `mcpServers` is present inline in both `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json`, `skills/unity-wrapper/SKILL.md` contains the full tool inventory and usage docs, `skills/unity-yaml-merge/SKILL.md` (ticket #41) carries the separate, MCP-free knowledge for git-merging Unity's YAML-serialized assets, and `skills/unity-xr-sim/SKILL.md` (ticket #54) carries the third, standalone skill for headset-free OpenXR mock-session testing.

## Contracts an agent won't infer from the tree

- **`unity-yaml-merge` is a second, deliberately separate skill (ticket #41), not a section of `unity-wrapper`.** It covers git-merging Unity YAML assets (scenes, prefabs, and similar) through the `UnityYAMLMerge`/SmartMerge driver — a git/CLI concern, not an editor-driving one. It exists as its own skill because `unity-wrapper`'s frontmatter description explicitly routes work *away* from reading serialized files, so merge-driver phrasing can't be folded into it without corrupting that routing; a test in `tests/skill-md.Tests.ps1` asserts `unity-wrapper`'s frontmatter stays free of merge-driver phrasing. It gets **no `mcpServers` entry** — it uses no MCP tool, only git/CLI. It also **carries no escalation policy by design**: it documents detection, wiring, invocation, and resolution mechanically, and deliberately says nothing about when a human should get involved — that decision belongs to whatever project consumes it, never to this plugin. `tests/unity-yaml-merge-skill.Tests.ps1` enforces this with a negative-assertion Describe over forbidden hand-off phrases.

- **`unity-xr-sim` is a third, standalone skill (ticket #54), teaching the headset-free OpenXR loop — Mock Runtime + Conformance Automation — layered on top of the editor `unity-wrapper` drives.** It rides `unityMCP`'s already-wired `execute_code`, `manage_editor`, and `read_console` tools rather than adding any MCP server or manifest entry of its own, so it needed no `mcpServers` change. `unity-wrapper`'s frontmatter stays free of XR-simulation phrasing (`unity-xr-sim`, `openxr`, `mock runtime`, `conformance automation`, `interaction profile`, `headset`) for the same disjoint-trigger-surface reason `unity-yaml-merge`'s frontmatter stays free of merge-driver phrasing — cross-referenced only from `unity-wrapper`'s `## What this skill is for` prose, asserted by `tests/skill-md.Tests.ps1` and `tests/unity-xr-sim-skill.Tests.ps1`. `skills/unity-xr-sim/XRSim.cs` ships a real, ready-to-adapt editor template (`Setup()`/`Restore()` pair backed by a whole-object JSON backup file, `Library/XRSim/openxr-settings-backup.json`, rather than a snapshot struct or activated-path bookkeeping — `Setup()` throws if a backup already exists (G3), `Restore()` throws if the backup is missing and never fabricates defaults (G4), per its own file header) rather than pseudocode-only documentation.

- **The wrapped MCP is external and inline, not a `.mcp.json`.** When wired, the MCP command goes into an inline `mcpServers` block in **both** `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json` (the two hosts can't share one external file — `${CLAUDE_PLUGIN_ROOT}` doesn't expand under Codex). Model it on `agent-serena-wrapper`, whose Claude manifest uses `--context claude-code` + `${CLAUDE_PROJECT_DIR}` and whose Codex manifest uses `--context codex` + `--project-from-cwd`.
- **Release is orphan-branch + marketplace dispatch.** `release.yml` (manual: Actions → release → `version=X.Y.Z`) stamps the version into both manifests, force-pushes an orphan `release` branch holding only install-ready files (including `hooks/`, ticket #47), and POSTs a dispatch (`category: skill`) to `Seretos/agent-marketplace`. `main` and `release` share no history. Clients install at the tag `agent-unity-wrapper--vX.Y.Z`.
- **`src/<TAG>` marker tags on `main` are what makes real release notes possible (ticket #48/#46/#45).** Because the orphan `release` branch shares no history with `main` (see above), two release tags on `release` have no merge-base and `gh api .../generate-notes` (or `--generate-notes`) has no commit range to diff — it silently returns empty notes. So every successful run of `release.yml` also pushes a lightweight tag `src/<TAG>` (e.g. `src/agent-unity-wrapper--v0.2.0`) onto the **unmodified `main` commit** the release was cut from, unconditionally, right before the orphan checkout. Release notes are then generated by diffing `src/<PREV_TAG>` → `src/<TAG>` — two real, connected `main` commits — and that body is written both to the GitHub Release (`gh release create --notes-file`, replacing `--generate-notes`) and forwarded to the marketplace dispatch as a `changelog` field.
  - **Pre-flight, before anything is staged or pushed:** `.github/scripts/prev-release-tag.sh <plugin-name> <version>` resolves the previous release tag by reading `git tag --list` on stdin (real SemVer 2.0.0 comparison, not `sort -V`), and `.github/scripts/preflight-check.sh <TAG> [<PREV_TAG>]` (same stdin contract) fails the run with `::error::` if `src/<TAG>` already exists (this release was already published), or if a resolved `<PREV_TAG>` has no `src/<PREV_TAG>` marker. Both scripts are pure decision logic — no `git`/`gh`/network calls of their own — which is what makes them unit-testable from a fixture tag list in `tests/test_release_scripts.py` without a real git repo.
  - **One-time manual bootstrap is required for the very first release cut after this contract landed**, because the workflow can never create `src/<PREV_TAG>` for a release that predates it: open that previous release tag's Actions run, read the `head_sha` it released from (the "Push orphan release branch and capture commit" step's log, or the commit the run checked out), then run once, locally or via `gh api`:
    ```
    git tag src/<PREV_TAG> <head_sha>
    git push origin src/<PREV_TAG>
    ```
    **The workflow must never attempt this automatically.** `GITHUB_TOKEN` cannot push a ref at a historical commit whose workflow-file tree differs from `main`'s current tip (GitHub blocks exactly this to stop a workflow from rewriting its own trigger surface after the fact) — so there is no automatic-backfill path, and none should be added; a missing marker is a preflight failure, not a fallback trigger.
  - `marketplace-payload.sh` builds the dispatch JSON via a single `jq -n` (never a heredoc) from `NAME`/`DESC`/`REPO`/`CATEGORY`/`VERSION`/`TAG`/`CHANGELOG` env vars, so a changelog body containing quotes, backslashes, `$(...)`, or embedded newlines round-trips exactly instead of being shell-interpolated; the `changelog` key is omitted entirely when there is no changelog (first release with no `PREV_TAG`).
- **Required secret:** `MARKETPLACE_DISPATCH_TOKEN` — fine-grained PAT, `Contents: RW` + `Pull requests: RW` on `Seretos/agent-marketplace` only.
- **Unity environments (worktree, main checkout, adopted) = status-dir isolation + a coupling to `agent-worktree`'s Environment model (ticket #47).** Each environment — a linked worktree (`environment_start environment_id=<id>`) or the repo's own main checkout (`environment_start checkout_path=<repo root>`) — drives its own Unity Editor with no "select instance" UI step, because both halves of the Unity MCP point at the same checkout-local `UNITY_MCP_STATUS_DIR`. A third case, a Unity Hub-started editor nobody launched via `environment_start`, is picked up by **adoption** instead (below) rather than by status-dir wiring.
  - The manifests set it in `unityMCP.env` — `${CLAUDE_PROJECT_DIR}/.unity-mcp` (Claude) and cwd-relative `.unity-mcp` (Codex; Codex has no `${CLAUDE_PROJECT_DIR}`, and the Python server resolves a relative value against its working dir = the checkout root). Both the C# bridge and Python server use the value **literally** (no `~`/relative rewriting on the Unity side), so the editor launch must pass an **absolute** path. This already reads correctly for both a linked worktree and the main checkout — `${CLAUDE_PROJECT_DIR}` resolves to whichever one Claude Code is rooted in — so the Environment-model migration needed **no manifest edit**.
  - The launch half lives in the **target Unity repo**, not here: `scripts/prepare-unity-worktree.ps1` writes a managed `start:`/`stop:` block into that repo's `.seretos/worktree-setup.yml` (the `agent-worktree` contract — this is the explicit cross-plugin coupling), adds `com.coplaydev.unity-mcp` to `Packages/manifest.json`, and ignores `.unity-mcp/`. `environment_start`/`environment_stop` then bring a headless Unity up/down per environment. Ownership of `.seretos/worktree-setup.yml` is existence-based, not content-based: the script creates the file only when it's absent; once it exists — managed block, foreign contract, or no `start:`/`stop:` at all — the script never touches it again, under any flag, including `-Force`: no write, no read, no advisory. Existence (`Test-Path`) is the only check ever made; the script never inspects an existing file's contents, so it gives no signal — not even a warning — about staleness or `isolation`. `environment_start` was chosen over `vdesktop` `launch_app` because that tool can't inject per-environment env (agent-vdesktop#59 / lib-python-vdesktop#28).
  - **`.seretos/unity-mcp-launch.ps1` is the opposite ownership model from `.seretos/worktree-setup.yml` — deliberately (ticket #47).** It carries the launch decision + Unity launch logic (editor resolution, the launch decision, cache server, Library mirror, pid file) and is generated by the same prepare-script — but unlike the yml, it is **always overwritten**, on every run, with no `-Force` gate and no existence check, so an updated launch implementation reaches every already-prepared repo the next time the prepare-script runs. It is tracked repo content (not gitignored). The managed `start:` steps in `worktree-setup.yml` shrink to thin call-sites into this file (`-Variant default|gui`); `stop:` stays inline. **`.seretos/unity-mcp-adopt.ps1` (ticket #52) joins this same always-overwritten contract**: a verbatim, always-regenerated copy of `scripts/unity-mcp-adopt.ps1`, dot-sourced by the generated launch script via `$PSScriptRoot` so both files sit side by side in `.seretos/`.
  - **Unity Hub adoption (ticket #52, rebuilt from #47) needs no manifest or status-dir change, no `prepare-unity-worktree.ps1` precondition, and no Windows privilege.** A human- or Hub-started editor writes into the *global* `~/.unity-mcp`, not the checkout-local one; adoption **copies** the matching instance's status file (filename-prefixed `unity-mcp-status-adopted-`, not a symlink) into `<checkout>/.unity-mcp` so the same status-dir contract above picks it up. Path matching is normalized (absolutized, separator/case-insensitive), not literal string equality; liveness is a TCP probe of the reported port, not a heartbeat-age gate. Lives in the plugin-owned `scripts/unity-mcp-adopt.ps1` (a real script, dot-sourceable and directly invokable — not a here-string), reached from two callers: `hooks/hooks.json`'s **`PreToolUse`** hook (matcher `mcp__.*unityMCP__.*`, runs before every unityMCP tool call — replaces the old `SessionStart` design, which could only adopt once per session and missed an editor started or restarted mid-session) and `environment_start`'s own launcher preamble, which dot-sources a verbatim copy materialized into `.seretos/unity-mcp-adopt.ps1` by the prepare-script (same always-overwritten ownership model as `.seretos/unity-mcp-launch.ps1`, added to that contract below). The script always exits 0 — a `PreToolUse` hook must never block the tool call it runs ahead of — and explains every rejected candidate on stdout. Codex has no hook surface; run the script by hand (`scripts/unity-mcp-adopt.ps1 -CheckoutPath <path>`) or rely on `environment_start`'s launcher pass. See `skills/unity-wrapper/SKILL.md`'s "Unity Hub adoption" section for the full contract.
  - **Bridge auto-start is NOT committable.** The bridge's `AutoStartOnLoad` is a Unity *EditorPref* (per-machine, hashed value name) — it does not survive a fresh clone and can't be set reliably outside Unity. So the start step boots the bridge deterministically via `-executeMethod MCPForUnity.Editor.McpCiBoot.StartStdioForCi` + `UNITY_MCP_ALLOW_BATCH=1` (modeled on CoplayDev's own CI) instead of relying on EditorPrefs.
  - **Flagged open items (per ticket #3, not pre-solved):** Unity editor binary resolution defaults to `UNITY_EDITOR_PATH`, else Unity Hub default install path derived from `ProjectVersion.txt` (OS-dependent); the bridge-package git pin (`#v9.7.1`) should track the server pin (`mcpforunityserver==9.7.1`); first-open `Library/` re-import is the real per-environment resource cost (consider capping concurrent Unity-enabled environments); the launch is **headless** (`-batchmode -nographics`) by default — switch to a GUI editor by editing the managed block if interactive editing is needed.
- **`assets/icon.png` and `description.md` are release artifacts, not just repo files.** The dispatch payload sends `raw.githubusercontent.com/${repo}/${TAG}/assets/icon.png` and `.../description.md` URLs to the marketplace, so both must live on the orphan `release` branch at the tagged commit — `release.yml`'s stage step copies them into the staging tree. Ship a real icon and a filled-in `description.md` before cutting v0.0.1 or the listing has no image / placeholder text.
- **`lint.yml` runs only on `pull_request`, not on every push.** A direct push to `main` triggers no CI at all — that's safe only because `main` is protected (merge via PR, with a required status check). If branch protection is (re)configured, the required-check context to select is the job id `validate` (the `jobs:` key in `lint.yml`), not the workflow's display name `lint`. `lint.yml` also carries a second job, `release-scripts` (ticket #48), which runs `tests/test_release_scripts.py` against the `.github/scripts/*.sh` release helpers on a `[ubuntu-latest, windows-latest]` matrix — it is advisory only (not yet added to branch protection); if it is added, select it by job id + matrix leg, i.e. the check contexts `release-scripts (ubuntu-latest)` / `release-scripts (windows-latest)`, the same job-id-not-display-name rule as `validate` above.
